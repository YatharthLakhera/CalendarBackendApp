## Lombok: what is actually in the compiled class

Lombok is an **annotation processor**. It rewrites the AST at compile time, so the
generated methods exist in the `.class` file but not in the `.java` file. Your IDE knows
this; a plain `javac` on a machine without Lombok on the annotation-processor path does
not, and you get "cannot find symbol: method getName()".

See what's really there:

```bash
mvn -o compile
javap -p target/classes/com/calendar/app/db/entity/UserDetails.class
```

You'll see `getUserId()`, `setUserId()`, `equals()`, `hashCode()`, `toString()`,
`canEqual()` — none of which appear in the source.

### `@Data` is five annotations

`@Data` = `@Getter` + `@Setter` + `@ToString` + `@EqualsAndHashCode` + `@RequiredArgsConstructor`.

That's a lot to accept implicitly, and three of the five cause real problems on entities.

### 🐞 `@Data` on a JPA entity: three separate landmines

Every entity in this project is `@Data`. That is convenient and it is also why
`EventAudience` needed hand-written `equals`/`hashCode` and a `@ToString.Exclude`.

**Landmine 1 — `toString()` infinite recursion.** `EventScheduler.toString()` prints its
`audiences`; each `EventAudience.toString()` would print its `event`; `StackOverflowError`.
Hence:

```java
@ToString.Exclude
@ManyToOne(fetch = FetchType.LAZY)
private EventScheduler event;
```

And remember the services log entities directly:

```java
log.info("eventScheduler : {}", eventScheduler);
```

So without that exclusion **the crash happens inside a log statement** — code that exists
purely to help you debug becomes the thing that takes the request down.

**Landmine 2 — `toString()` triggers lazy loading.** Printing an entity walks every field,
including lazy collections. A single `log.info` can fire a burst of `SELECT`s, or throw
`LazyInitializationException` if the session is closed. **Logging an entity is never free.**
Log the id and the two fields you care about.

**Landmine 3 — `equals`/`hashCode` on entities is genuinely hard.** Which brings us to:

### Why that strange `equals`/`hashCode` exists

```java
// EventAudience
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (o == null || Hibernate.getClass(this) != Hibernate.getClass(o)) return false;
    EventAudience that = (EventAudience) o;
    return Objects.equals(id, that.id);
}

@Override
public int hashCode() {
    return getClass().hashCode();
}
```

This looks wrong. It is (mostly) the recommended pattern for JPA entities, and here's why:

**Why `Hibernate.getClass(this)` instead of `this.getClass()`?**

Hibernate returns **proxies** for lazily-loaded entities — runtime subclasses generated by
Byte Buddy, named things like `EventAudience$HibernateProxy$aBc123`. So
`proxy.getClass() != EventAudience.class`, and a naive `getClass() != o.getClass()` check
makes an entity **not equal to itself** depending on how it was loaded.
`Hibernate.getClass(...)` unwraps the proxy to the real class. `instanceof` would also
work; `getClass()` alone would not.

**Why `hashCode()` returns a constant?**

Because an entity's `id` **changes during its lifetime**. Before `save()`, `id` is `0` (or
`null`). After the flush, the database assigns a real value. If `hashCode()` depended on
`id`, then:

```java
Set<EventAudience> set = new HashSet<>();
set.add(audience);              // hashed into bucket for id=0
repository.save(audience);      // id becomes 42 → hashCode changes
set.contains(audience);         // false! It's in the wrong bucket.
```

The object is now **lost inside a `HashSet` that contains it**. This is the single
nastiest ORM bug there is, and a constant `hashCode` prevents it by guaranteeing the hash
never changes.

**The price**: every instance lands in the same bucket, so `HashSet`/`HashMap` degrade
from O(1) to O(n). That's an accepted trade — entity collections are small — but it is
exactly what makes `new HashSet<>(this.audiences)` in `removeAllAudiences()` a poor
choice ([08](08-code-walkthrough.md#eventschedulerremoveallaudiences)).

⚠️ One real weakness remains: `equals` compares `id`, and `id` is `0` for **every** unsaved
`EventAudience`. So all new audiences are equal to each other. The canonical fix is a
client-assigned "business key" (a UUID generated in the constructor, not by the DB) — which
is, incidentally, another argument for `GenerationType.UUID` over `IDENTITY`.

**The three other entities (`UserDetails`, `EventScheduler`, `UserCustomAvailability`) use
Lombok's default `@Data` `equals`/`hashCode`, which compares *all fields*.** That is worse
in every way — it's mutable, it triggers lazy loads, and it can recurse. Only
`EventAudience` was fixed, presumably because it's the one that got put in a `HashSet`.

### `@NoArgsConstructor` isn't optional on entities

```java
@Data @Entity @NoArgsConstructor
public class UserDetails {
    public UserDetails(UserRequest userRequest) { ... }
}
```

JPA instantiates entities reflectively and **requires** a no-arg constructor. In Java,
declaring *any* constructor removes the implicit default one. So the moment
`UserDetails(UserRequest)` was written, the no-arg constructor vanished and had to be added
back. Jackson has the same requirement for deserialization — which is why every DTO in
`models/api/` also carries `@NoArgsConstructor`.

Notice `UserResponse` and `EventSchedulingResponse` **don't** have it. They're
response-only — never deserialized, never loaded by JPA — so they don't need it. That
absence is meaningful, not an oversight.

### `@Slf4j`

```java
@Slf4j
public class UserService {
    // log.info(...) — where did `log` come from?
}
```

Generates:

```java
private static final org.slf4j.Logger log = org.slf4j.LoggerFactory.getLogger(UserService.class);
```

`static final` matters: one logger per class, not per instance.

**Always use `{}` placeholders, never string concatenation:**

```java
log.info("userDetails : {}", userDetails);        // ✅ toString() only if INFO is enabled
log.info("userDetails : " + userDetails);         // ❌ toString() always, even at WARN
```

With concatenation the string is built *before* the call, so you pay for it even when the
level is disabled. Given landmines 1 and 2 above, on an entity that cost can be a burst of
SQL queries — for a line that gets thrown away.

### `@NoArgsConstructor(access = AccessLevel.PRIVATE)` on utilities

```java
@NoArgsConstructor(access = AccessLevel.PRIVATE)
public class AvailabilityUtility { /* only static methods */ }
```

Generates a private constructor so nobody can instantiate a namespace. Standard idiom.

## Jackson: the naming rules nobody tells you

### The `isAvailable` trap

This is the highest-value item in this file. Three names for one thing:

```java
// UserCustomAvailability / CustomAvailabilityModel
private boolean isAvailable;
```

| Layer | Name | Determined by |
|---|---|---|
| Java field | `isAvailable` | you |
| MySQL column | `is_available` | Hibernate's `CamelCaseToUnderscoresNamingStrategy` (reads the **field**) |
| JSON property | **`available`** | Jackson (reads the **getter** `isAvailable()` and strips `is`) |

Jackson derives property names from **accessor methods**, not fields. For a `boolean`,
Lombok generates `isAvailable()`, and Jackson's bean-naming convention strips the `is`
prefix → `available`.

So the API contract is:

```json
{ "available": true }        ✅
{ "isAvailable": true }      ❌ silently ignored → field stays false → "blocked all day"
```

By default Jackson **ignores unknown properties**, so the wrong key produces a `200 OK` and
completely wrong data. You proved this to yourself in
[05-user-flows.md](05-user-flows.md#24-a-custom-override--bala-takes-a-half-day).

Three defences, and you want all three:
1. Don't prefix boolean fields with `is` — name it `available`.
2. Be explicit at the boundary: `@JsonProperty("available")`.
3. Fail loudly on typos: `spring.jackson.deserialization.fail-on-unknown-properties=true`.
   (Consider the compatibility cost — clients can no longer send extra fields — but for an
   internal API it catches a whole class of silent bugs.)

### Any getter becomes a JSON property

```java
@JsonIgnore
public List<String> getWeeksAvailability() { ... }
```

`getWeeksAvailability()` is a computed helper. Without `@JsonIgnore`, Jackson would emit
`"weeksAvailability": [...]` in every response **and** in the stored JSON column, then fail
trying to set it on the way back in.

**Reflex to build: every computed `getXxx()` on a serialised class needs `@JsonIgnore`.**

Same idea, different motive:

```java
// AvailabilityBucket
@JsonIgnore private int startTimeValue;
@JsonIgnore private int endTimeValue;
```

These are internal to the algorithm. Hiding them keeps the public contract minimal —
**every field you emit is a field a client will depend on and you can never remove.**

### `@JsonBackReference` and cycles

`EventScheduler` → `audiences` → each `EventAudience` → `event` → back to the start.
Jackson would recurse until the stack blows. `@JsonBackReference` marks the child→parent
side as "don't serialise this", breaking the cycle.

The alternative pair is `@JsonManagedReference` (parent side) + `@JsonBackReference` (child
side), or `@JsonIdentityInfo` if you genuinely need both directions. In practice, the best
answer is **don't serialise entities at all** — map to DTOs, which is what this project
does everywhere except `UserDefaultAvailability`. Once you use DTOs, cycles are impossible
by construction.

### Custom serializers vs. the type system

`CustomDateSerializer` / `CustomDateDeserializer` exist only because the project uses
`java.util.Date`. Switch to `java.time.LocalDate` and both disappear —
`jackson-datatype-jsr310` (already a transitive dependency via
`spring-boot-starter-json`) handles ISO dates natively. **Choosing a better type deletes
code.** That's usually the sign of a good refactor.

## `java.util.Date` in 2024

The project uses `java.util.Date` throughout: entities, DTOs, `DateUtility`,
`AvailabilityUtility`. It's the legacy API, superseded by `java.time` in **Java 8** —
about a decade before this code was written.

Why it matters here specifically:

**1. `Date` is mutable.** Any caller holding a reference can mutate it. `LocalDate` is
immutable, so it's inherently thread-safe and safe to share.

**2. `Date` is really an instant, not a date.** It's a millisecond offset from the epoch —
it *has* a time and a timezone whether you want one or not. That's why
`@Temporal(TemporalType.DATE)` is needed to tell Hibernate "truncate this". With
`LocalDate`, "a date with no time" is expressible in the type system and the annotation is
unnecessary.

**3. It forces `SimpleDateFormat`, which is not thread-safe.** Two `static
SimpleDateFormat` fields in this repo are live concurrency bugs
([08](08-code-walkthrough.md#controllerdeserializercustomdatedeserializerjava-and-controllerserializercustomdateserializerjava)).
`DateTimeFormatter` is immutable and thread-safe by design.

**4. `equals` asymmetry.** `java.sql.Timestamp.equals(java.util.Date)` and the reverse can
disagree. That breaks `HashMap`, `List.contains`, and `Set` in ways that look impossible.
The project's `customAvailabilityMap.containsKey(currentDate)` in `AvailabilityUtility`
lives one type change away from this
([07](07-lld-availability-engine.md#default-vs-custom-per-day)).

**5. It's timezone-dependent where you don't want it to be.** `DateUtils.addDays` across a
DST boundary can shift the wall-clock time. `LocalDate.plusDays()` cannot — it has no
concept of hours.

For a **calendar application**, using the timezone-ambiguous date API is the wrong default.
The migration is mechanical (`Date` → `LocalDate`, `@Temporal` deleted, both custom
serializers deleted, `DateUtility` → `LocalDate.parse`) and it deletes more code than it
adds.

## Hibernate details that will surprise you

### `save()` doesn't mean `INSERT`

`JpaRepository.save()` calls `persist()` for a new entity and `merge()` for a detached
one, and neither necessarily issues SQL immediately. Statements go out at **flush**, which
happens at transaction commit or before a query that might be affected. See
[02](02-request-lifecycle.md#step-6--hibernate-the-persistence-context-and-the-flush).

### Dirty checking means you can update without calling `save`

Inside a transaction, Hibernate snapshots every loaded entity and compares at flush time.
Mutating a managed entity issues an `UPDATE` whether or not you called `save()`. This is
either magical or terrifying depending on whether you know about it.

### Lazy vs. eager defaults are inconsistent

| Relationship | Default fetch |
|---|---|
| `@OneToMany` | `LAZY` |
| `@ManyToMany` | `LAZY` |
| `@ManyToOne` | **`EAGER`** |
| `@OneToOne` | **`EAGER`** |

There is no principle behind this; memorise it. `EventAudience.event` is explicitly marked
`FetchType.LAZY` to override the `@ManyToOne` default. `EventAudience.user` is `@OneToOne`
and therefore **eager** — every audience row loaded pulls its user in the same breath. For
this app that's usually what you want (the response needs the user), but it's a decision
being made by a default, not by a person.

### `LazyInitializationException`

Touch a lazy collection after the persistence context closes and Hibernate throws. It
doesn't happen here because `spring.jpa.open-in-view` defaults to `true` — Spring Boot
keeps the `EntityManager` open for the entire request, including JSON serialisation.

That default is convenient and widely criticised: it holds a database connection for the
whole request (including the time spent writing bytes to a slow client), and it hides N+1
problems by making lazy loads always "work". Turning it off
(`spring.jpa.open-in-view=false`) is standard production hardening — and it would break
`isOrganisedBy()` until the event query explicitly fetched its audiences.

### `@Transactional` only works through the proxy

Spring implements it with an AOP proxy. **Self-invocation (`this.someTransactionalMethod()`)
bypasses the proxy entirely and the annotation is silently ignored.** No error. Also, it
only works on `public` methods by default. This is the most common Spring gotcha there is.

## Java language details this project depends on

### `protected` is wider than package-private

```java
protected UserDetails getUserFor(final UUID userId)
```

The javadoc says "only accessible in service package". Precisely:

```
private  <  (no modifier)  <  protected  <  public
             package-private   package + subclasses anywhere
```

`protected` grants package access **plus** subclass access from any package. If you want
package-only, write no modifier at all. Most people believe `protected` is narrower than
package-private; it is not.

### `Optional` is a return type, not a field type

```java
Optional<UserDetails> findByEmail(String email);
```

```java
Optional<UserDetails> userDetails = userRepository.findByEmail(email);
if (userDetails.isPresent()) {
    return userDetails.get();
}
throw new UserNotFound();
```

Correct, but not idiomatic. The whole block is:

```java
return userRepository.findByEmail(email).orElseThrow(UserNotFound::new);
```

`isPresent()` + `get()` is `Optional` used as a nullable box — it gets you the null-safety
but none of the expressiveness. Learn `orElseThrow`, `map`, `orElseGet`, `ifPresent`. And
never use `Optional` as a field or a parameter type; it isn't `Serializable` and it adds
noise where plain `null` plus a check is clearer.

### `Integer` vs `int`, deliberately

```java
Integer start = null;   // null means "no run in progress"
```

Boxing used as a sentinel — a legitimate technique. Costs: heap allocation, and every
comparison risks an NPE on auto-unboxing. Also note `Integer.valueOf` caches −128..127, so
`==` on boxed integers works for small values and fails for large ones — the classic
`Integer a = 1000, b = 1000; a == b` → `false`. Always `.equals()` on boxed types.

### Enums are singletons, so `==` is correct

```java
audience.getRole() == UserEventRole.ORGANISER      // ✅ and preferable
audience.getRole().equals(UserEventRole.ORGANISER) // works, but NPEs on null
```

`==` is null-safe here; `.equals()` isn't. For enums, prefer `==`.

Contrast in the very same expression:

```java
user.getUserId().equals(audience.getUser().getUserId())   // ✅ UUID is a value object
user.getUserId() == audience.getUser().getUserId()        // ❌ compares references
```

### `Collections.rotate` mutates in place

```java
Collections.rotate(weeksAvailability, -dayOfWeek.getValue());
```

Returns `void`; modifies the list you pass. Safe here **only because**
`getWeeksAvailability()` returns a fresh `ArrayList` each call. Change that method to
cache or return a shared list, and this line quietly corrupts the entity for every
subsequent participant in the loop. **Mutating a value you got from a getter is a bet on
that getter's implementation.**

### `ConcurrentModificationException` isn't about threads

```java
for (EventAudience audience : new HashSet<>(this.audiences)) {
    remove(audience);   // mutates this.audiences
}
```

Removing from a collection while iterating it throws `ConcurrentModificationException` on a
single thread. The defensive copy is why this works. (See
[08](08-code-walkthrough.md#eventschedulerremoveallaudiences) for why a `HashSet` copy
specifically is a poor choice.)

### `Arrays.fill(matrix, 0)` is redundant — and knowing why matters

Java guarantees default initialisation: `0` for numeric types, `false` for `boolean`,
`null` for references, always, for both fields and array elements. `new int[288]` is
already all zeros. (In C, `malloc` gives you garbage — that's where the habit comes from.)

## The dependency that isn't declared

Run this:

```bash
grep -rl "org.apache.commons.lang3" src/main/java | wc -l    # 8 files
grep -n "commons-lang3" pom.xml                              # nothing
```

**Eight files import `org.apache.commons.lang3` and `pom.xml` never declares it.** Core
business logic — `AvailabilityUtility`, `AvailabilityParseUtility`, `StringUtility`,
`AvailabilityPatternValidator`, `AvailabilityBucket`, `AvailabilityService`,
`UserDefaultAvailability`, `GlobalExceptionHandler` — depends on a library the project
never asked for.

Where does it come from? `mvn dependency:tree` answers it:

```
org.springdoc:springdoc-openapi-starter-webmvc-ui:2.0.2
 └─ springdoc-openapi-starter-webmvc-api
     └─ springdoc-openapi-starter-common
         └─ io.swagger.core.v3:swagger-core-jakarta:2.2.7
             └─ org.apache.commons:commons-lang3:3.14.0     ← here
```

**The application's business logic compiles only because a documentation UI happens to
depend on a string library, four levels down.**

Consequences, all real:
- Remove Swagger (a perfectly reasonable production decision — see
  [11](11-production-gaps.md#swagger-is-publicly-exposed)) and **the project stops
  compiling**, with errors in files that have nothing to do with Swagger.
- Upgrade springdoc and `commons-lang3` may change major version underneath you.
- Nobody reading `pom.xml` can tell that `StringUtils` is available.

This is called a **transitive dependency leak**, and the rule is simple:

> **If you `import` it, declare it.**

The fix is three lines:

```xml
<dependency>
    <groupId>org.apache.commons</groupId>
    <artifactId>commons-lang3</artifactId>
</dependency>
```

(No `<version>` needed — `spring-boot-starter-parent` manages it. That's what a
dependency-management BOM is *for*, and it's why the other Spring dependencies have no
versions either.)

Enforce it automatically with `maven-dependency-plugin`'s `analyze` goal, which fails the
build on "used undeclared" and warns on "declared unused". It would flag both problems
here — because the reverse also applies:

```xml
<dependency>
    <groupId>commons-io</groupId>
    <artifactId>commons-io</artifactId>
    <version>2.17.0</version>
</dependency>
```

`commons-io` is declared and **imported nowhere**. Dead weight in the JAR, plus a
dependency you now have to patch when it gets a CVE.

### Related: the MySQL driver coordinates are stale

```xml
<groupId>mysql</groupId>
<artifactId>mysql-connector-java</artifactId>
<version>8.0.33</version>
```

But `mvn dependency:tree` resolves it as `com.mysql:mysql-connector-j:8.0.33`. Oracle
**relocated** the artifact; the old coordinates are a stub that redirects. It works, but
it's deprecated and won't receive new versions. Use `com.mysql:mysql-connector-j`, and drop
the `<version>` — Spring Boot's parent manages it, and pinning it by hand means you'll
silently fall behind on security patches when you upgrade Boot.

Also, a JDBC driver is only needed at **runtime**, not compile time, so it should be
`<scope>runtime</scope>`. That prevents anyone accidentally importing
`com.mysql.cj.*` in application code and coupling your business logic to a specific
database.

### `<optional>true</optional>` on Lombok

```xml
<dependency>
    <groupId>org.projectlombok</groupId>
    <artifactId>lombok</artifactId>
    <optional>true</optional>
</dependency>
```

`optional` means "don't leak this to projects that depend on me". Correct, because Lombok
is compile-time only — its annotations have `SOURCE` retention and nothing needs it at
runtime. The `spring-boot-maven-plugin` `<excludes>` block in `pom.xml` reinforces this by
keeping the Lombok JAR out of the fat JAR. Two mechanisms, same intent — this part of the
build is done thoughtfully.
