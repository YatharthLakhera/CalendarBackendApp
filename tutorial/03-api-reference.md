# 03 — API Reference

Every endpoint in the project, with its exact signature, what it does, and where it's
sharp. Base URL for local runs: `http://localhost:8080`.

## The authentication model (read this first)

Every "who am I" endpoint takes the caller's identity from a plain HTTP header:

```java
@RequestHeader("userId") UUID userId
```

⚠️ **There is no authentication in this project.** Anyone who knows or guesses a UUID is
that user. There is no password, no token, no signature, no session. Send someone else's
UUID and you *are* them: you can read their availability, change their default schedule,
book meetings as them, and delete their events.

Why it's built this way: this is a take-home-style / demo backend, and auth was
deliberately out of scope. That is a legitimate scope cut — you cannot build everything.
What is **not** legitimate is shipping it to a public IP without noticing.

Why UUID is nonetheless a good choice here: the alternative,
`AUTO_INCREMENT` integer IDs, leaks information (user #4212 tells you the service has
~4212 users) and makes enumeration trivial — walk 1, 2, 3... and you have every account.
A random 128-bit UUID is not guessable by brute force. It's the *right primitive*, wired
up the *wrong way* (an identifier is not a credential).

What real auth looks like and how you'd add it:
[11-production-gaps.md](11-production-gaps.md#no-authentication-or-authorisation).

## User API — `UserController`

### `POST /user` — create a user

```java
public UserResponse addUserFor(@Valid @RequestBody UserRequest userRequest)
```

Request:
```json
{ "name": "Asha", "email": "asha@example.com" }
```

Response `200`:
```json
{ "name": "Asha", "email": "asha@example.com", "id": "1728dfe4-a197-47bf-9c4c-c80011c58f9e" }
```

- `@Valid` is present, so `@NotNull` on `name` and `@Email`/`@NotNull` on `email`
  (declared in `UserUpdateRequest` / `UserRequest`) are enforced → `400` on violation.
- The UUID is generated by Hibernate (`@GeneratedValue(strategy = GenerationType.UUID)`),
  not by MySQL, and not by your code.

🐞 **Email is not unique.** There is no unique constraint in `db_schema.sql` and no
duplicate check in `UserService.addUserFor`. Post the same email twice and you get two
users. Then `UserRepository.findByEmail` — which returns `Optional<UserDetails>` —
receives 2 rows from the DB and Spring Data throws
`IncorrectResultSizeDataAccessException`, surfacing as a **500** on every subsequent
search or booking involving that address. One missing `UNIQUE KEY` breaks the whole
booking flow. Reproduce it; it takes 30 seconds and the lesson sticks.

### `GET /user` — get yourself

```java
public UserResponse getUserFor(@RequestHeader("userId") UUID userId)
```

`404` (`"User Not Found"`) if the UUID doesn't exist.

### `GET /user/search?email=...` — find a user by email

```java
public UserResponse searchUserFor(@RequestParam("email") String email)
```

The README is honest about why this exists: nobody can remember a UUID, and you need a
way to look up participants before booking. But note:

⚠️ **This endpoint requires no `userId` header at all.** It is a completely unauthenticated
email → (name, UUID) lookup. Anyone can confirm whether a given email is registered, and
retrieve that account's UUID — which, given the auth model above, *is* the credential.
This is the most severe issue in the API surface.

### `PUT /user` — update your name

```java
public UserResponse updateUserFor(@RequestHeader("userId") UUID userId,
                                  @Valid @RequestBody UserUpdateRequest request)
```

Request: `{ "name": "Asha Rao" }`

Email is intentionally immutable (README: "Email cannot be changed as that's a critical
piece of information which helps in booking appointment"). Note *how* immutability is
enforced: `UserUpdateRequest` simply has no `email` field, so there is nothing to send.
**Enforcing a rule through the shape of a type is stronger than enforcing it with an
`if`** — you cannot forget to check something that cannot be expressed. Remember this
technique; it generalises far beyond this project.

## Availability API — `AvailabilityController`

### `PUT /availability/defaults` — set your weekly recurring schedule

```java
public void updateUserDefaultAvailabilityFor(@RequestHeader("userId") UUID userId,
                                             @RequestBody UserDefaultAvailability userRequest)
```

Request:
```json
{
  "timeZone": "IST",
  "monday":    "1000:1100;1300:1800",
  "tuesday":   "1000:1100;1300:1800",
  "wednesday": "1000:1100;1300:1800",
  "thursday":  "1000:1100;1300:1800",
  "friday":    "1000:1100;1300:1800",
  "saturday":  "",
  "sunday":    ""
}
```

**The availability string format** — you will see this everywhere:

```
1000:1100;1300:1800
└──┘ └──┘ └──┘ └──┘
start end  start end     ";" separates ranges, ":" separates start from end
```

Times are `HHMM` in 24-hour form, as **strings**, and must be multiples of 5 minutes.
`"0930:1015"` is valid; `"0932:1015"` is rejected; `"930:1015"` breaks parsing.

Validated by `AvailabilityPatternValidator` (a Jackson deserializer): start < end, both
multiples of 5. See [02-request-lifecycle.md](02-request-lifecycle.md#jackson-deserialization--and-a-project-specific-twist)
for why those validation errors don't come back as clean 400s.

Notes:
- Returns `void` → HTTP `200` with an empty body. A `PUT` that returns nothing is fine,
  but returning the updated resource is friendlier (saves the client a `GET`).
- This is a **full replace**, not a merge. Omit `"friday"` and Friday becomes `null` →
  treated as "no availability". There is no way to update one day in isolation.
- ⚠️ `timeZone` is accepted, stored, and **never used**. The whole system assumes IST.
- Stored as a JSON blob in `user_details.default_availability` — see
  [04-db-schema-and-orm.md](04-db-schema-and-orm.md#design-decision-3-the-json-column-and-convert).

### `GET /availability/defaults` — read your weekly schedule

```java
public UserDefaultAvailability getDefaultAvailabilityFor(@RequestHeader("userId") UUID userId)
```

Returns `null` (literally, an empty body) if you never set one. ⚠️ Returning a bare
`null` for "not configured" forces every client to null-check; `{}` or an explicit
`"configured": false` would be kinder.

### `PUT /availability/custom` — override a single date

```java
public void updateUserAvailabilityFor(@RequestHeader("userId") UUID userId,
                                      @RequestBody CustomAvailabilityModel request)
```

Request:
```json
{ "date": "2024-12-11", "timeZone": "IST", "availability": "1000:1100;1300:1800", "available": true }
```

- The JSON key is **`available`**, not `isAvailable`, even though the Java field is
  `isAvailable`. See [09-java-gaps.md](09-java-gaps.md#the-isavailable-trap).
- `"available": false` means "blocked all day" — the `availability` string is ignored
  (`AvailabilityUtility` substitutes `""`). That's how you model a holiday.
- A custom entry **completely overrides** the default for that date. Not merged, not
  intersected — replaced.
- Upsert semantics: the service looks for an existing row for `(userId, date)` and updates
  it, else inserts.

🐞 The upsert is **not atomic**. `findByUserIdAndAvailabilityDate` then `save` is
read-then-write with no lock and no unique constraint on `(user_id, availability_date)` —
the schema declares only a plain `KEY` (an index), not a `UNIQUE KEY`. Two concurrent
requests for the same date both find nothing and both insert, and now the date has two
rows. Then `AvailabilityUtility` calls `Collectors.toMap(...)` keyed by date and throws
`IllegalStateException: Duplicate key`, breaking the availability API for that user.
Fix: add `UNIQUE KEY (user_id, availability_date)`. This is the *classic* concurrency bug
and you will meet it again in your career.

### `GET /availability/{fromDate}/{windowType}?emails=a@x.com,b@y.com` — the core endpoint

```java
public AvailabilityResponse getAvailabilityFor(@RequestHeader("userId") UUID userId,
                                               @PathVariable("fromDate") String fromDate,
                                               @PathVariable("windowType") AvailabilityWindowType windowType,
                                               @RequestParam(value = "emails", required = false) String emailList)
```

This is the heart of the product: *when can all of us meet?*

```
GET /availability/2024-12-11/DAY
GET /availability/2024-12-11/WEEK?emails=bala@example.com,chen@example.com
```

- `fromDate`: `yyyy-MM-dd`. Parsed by `DateUtility.parseDate`, which throws
  `BadRequestException` → clean `400`. (Contrast with the deserializer path above — this
  one works properly, because the exception is thrown from controller code, not from
  inside Jackson.)
- `windowType`: `DAY` (1 day) or `WEEK` (7 days). Case-sensitive.
- `emails`: optional, comma-separated. Omit it and you get only your own availability.

Response:
```json
{
  "availabilityBuckets": [
    { "date": "2024-12-11", "startTime": "1000", "endTime": "1100" }
  ],
  "events": [
    { "eventId": "...", "title": "...", "eventDate": "2024-12-11",
      "startTime": "1400", "endTime": "1500", "timeZone": "IST",
      "audienceRes": [ { "user": {...}, "role": "ORGANISER", "status": "ACCEPTED" } ] }
  ]
}
```

`availabilityBuckets` = intersection of everyone's free time (defaults or custom
overrides), minus every slot already booked. `events` = only the events **you** organise —
a deliberate privacy decision, filtered in `AvailabilityUtility.availabilityResponseBuilder`
via `event.isOrganisedBy(organiser)`.

Sharp edges — all covered in depth in [07-lld-availability-engine.md](07-lld-availability-engine.md):

- 🐞 The weekday rotation is off by one, so `monday`'s configured hours are applied to
  Tuesday's request. This is the most impactful bug in the repo.
- 🐞 Unknown emails are **silently dropped**. `getUserFor(List<String>)` calls
  `findByEmailIn`, which returns only matching rows. Typo a participant's address and you
  get availability for a smaller group, with no error — a wrong answer that looks right.
- ⚠️ The event query joins without `DISTINCT`, so an event attended by three of your
  participants appears **three times** in the `events` array. (It doesn't corrupt the
  slots — see [07](07-lld-availability-engine.md#the-service-side-what-feeds-the-engine).)
- ⚠️ Range ends are **inclusive**, so a 10:00–11:00 meeting blocks the instant 11:00. The
  README documents this ("other meetings can have starttime at `11:05`").
- ⚠️ No cap on how many emails you can pass. 500 emails = 500 users loaded and a
  500× larger intersection computation, on a request anyone can send.

## Event API — `EventSchedulerController`

### `POST /event` — book a meeting

```java
public EventSchedulingResponse addEventFor(@RequestHeader("userId") UUID userId,
                                           @RequestBody EventSchedulingRequest request)
```

Request:
```json
{
  "title": "Design review",
  "description": "Discuss the availability engine",
  "eventDate": "2024-12-11",
  "startTime": "1000",
  "endTime": "1100",
  "timeZone": "IST",
  "audienceReq": [
    { "email": "bala@example.com", "role": "PARTICIPANT" }
  ]
}
```

The caller (`userId` header) is automatically added as `ORGANISER` with status
`ACCEPTED` — you don't list yourself in `audienceReq`. Everyone else starts `PENDING`.

🐞 **Booking does not check availability.** Read `EventSchedulerService.addEventFor`: it
loads users, builds the event, saves. It never calls `AvailabilityService`. You can book
10:00–11:00 for a participant who is already booked 10:00–11:00, or who has marked
themselves unavailable that day, or at 03:00 on a Sunday. The availability endpoint is
*advisory only*. See [11-production-gaps.md](11-production-gaps.md#double-booking-is-not-prevented)
— including why fixing it needs more than an `if`.

⚠️ No validation at all on this body: `null` title, `endTime` before `startTime`, times
that aren't multiples of 5, a date in 1970, an empty audience — all accepted. No `@Valid`,
and `EventSchedulingRequest` carries no constraint annotations. Note that
`AvailabilityPatternValidator` guards the *availability* strings but nothing guards the
*event* times, so the event API is looser than the availability API it's supposed to
complement.

### `PUT /event/{eventId}/update` — reschedule

```java
public EventSchedulingResponse rescheduleEventFor(@RequestHeader("userId") UUID userId,
                                                  @PathVariable("eventId") UUID eventId,
                                                  @RequestBody EventSchedulingRequest request)
```

Organiser only — else `ActionNotAllowed` → 🐞 `500` (should be `403`).

Behaviour worth knowing:
- **The audience list is replaced wholesale.** All existing `event_audience` rows are
  removed and rebuilt from the request. Everyone's RSVP status resets to `PENDING`
  (except the organiser). Omit a participant and they are removed from the meeting.
- ⚠️ `EventScheduler.update()` copies `title`, `description`, `startTime`, `endTime`,
  `timeZone` — but **not `eventDate`**. You cannot move a meeting to a different day
  through this endpoint; the field is silently ignored. Compare `update()` to the
  constructor right above it in `EventScheduler.java` — the constructor sets `eventDate`,
  `update` doesn't. Deliberate or a copy-paste miss? Nothing in the code says. That
  ambiguity is itself the lesson: a one-line comment would have settled it forever.
- This is the only `@Transactional` method in the project, and it needs to be.

### `GET /event/{eventId}` — read an event

```java
public EventSchedulingResponse getEventFor(@PathVariable("eventId") UUID eventId)
```

⚠️ **No `userId` header, no permission check.** Anyone with an event UUID can read its
title, description, and the name/email/RSVP of every attendee. This directly contradicts
the README's stated assumption that "Users cannot see events of other users" — a rule the
availability endpoint carefully enforces and this endpoint doesn't. Two endpoints
disagreeing about the same rule is exactly what happens when a rule lives in people's
heads instead of in one place in the code.

### `PUT /event/{eventId}/status/{status}` — RSVP

```java
public void updateEventStatus(@RequestHeader("userId") UUID userId,
                              @PathVariable("eventId") UUID eventId,
                              @PathVariable("status") EventStatus status)
```

`status` ∈ `PENDING | ACCEPTED | MAYBE | DECLINED`. You must be in the event's audience,
else `ActionNotAllowed` (→ 500). Sensible REST would use `PATCH` with a body, but the
path-variable form is common and unambiguous.

⚠️ A `DECLINED` status has **no effect on availability**. `AvailabilityUtility` blocks a
slot for every event returned by the query regardless of RSVP. Decline every meeting you
like — your calendar still shows as busy. This is a real product bug hiding in a data
model that *does* record the answer; nothing reads it.

### `DELETE /event/{eventId}` — cancel

```java
public void deleteEventFor(@RequestHeader("userId") UUID userId, @PathVariable("eventId") UUID eventId)
```

Organiser only. A **hard delete** — the row is gone, along with its `event_audience`
children via `cascade = CascadeType.ALL`. No audit trail, no "who cancelled my meeting
and when". Production systems overwhelmingly prefer **soft deletes** (`deleted_at`
timestamp, filtered out of queries) precisely because "the data is just gone" is an
unanswerable support ticket.

## Status codes, honestly

What the code actually returns today:

| Situation | Returned | Should be |
|---|---|---|
| Success | `200` | `200`, or `201` for `POST /user` and `POST /event` |
| Unknown user / event | `404` | `404` ✅ |
| Bad date in path | `400` | `400` ✅ |
| Failed `@Valid` on user endpoints | `400` | `400` ✅ |
| Bad availability pattern | 🐞 `500` (wrapped by Jackson) | `400` |
| Not the organiser | 🐞 `500` | `403` |
| Duplicate email in DB | 🐞 `500` | `409` on create |
| Anything unexpected | `500` + `ex.getMessage()` | `500` + generic message + correlation ID |

Four of eight rows wrong is normal for a first version and completely fixable — see
[13-exercises.md](13-exercises.md).

## Cross-cutting: what's missing from the whole API

- **No pagination anywhere.** Nothing returns a list that could grow unbounded *today*,
  but `events` in the availability response grows with the window, and there's no
  `?page=&size=`. Add pagination before the list gets big, not after.
- **No API versioning.** No `/v1/` prefix. The moment a mobile app ships against this,
  every response shape is frozen forever — you can only add fields, never rename or
  remove. `/v1/` costs nothing now and buys you an escape hatch later.
- **No rate limiting.** `GET /availability/.../WEEK?emails=<500 addresses>` is a cheap
  request that causes expensive work.
- **No idempotency.** Retry a `POST /event` after a timeout and you get two meetings.
  Networks time out constantly; clients retry. The standard fix is an
  `Idempotency-Key` header the server remembers.
- **No `Content-Type` discipline on errors.** Fine here, but worth checking on any API.
